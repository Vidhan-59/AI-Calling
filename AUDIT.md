## Bottom line

This is not a blank project and not a rough prototype. It is **two systems sharing one folder**, and the repo's own README says this explicitly (it's worth reading if you haven't lately): a small, working, currently-runnable Claude+Twilio voice agent, and a much larger, well-designed but **not-yet-wired-up** rebuild toward the ShiftEaze multi-agent platform. The master prompt's requirements (streaming STT/LLM/TTS pipeline, barge-in, dialer queue, compliance gate, concurrency) map almost entirely onto the second system — and that system currently has no telephony entrypoint, no dialer, no admission-control/compliance gate, and no way to actually place a call. Nothing here needs to be thrown away; a lot of the target architecture is already sketched out correctly. But "single outbound call working end-to-end" (Phase 3) is not a small step from here — the two live call paths that exist today don't touch any of that scaffolding.

## What currently works (verified: read + pytest, not a live call — see Secrets)

**Track A — the "simple agent"** (`main.py`, `routers/agents.py`, `routers/calls.py`, `routers/voice.py`, `services/agent_manager.py`, `services/claude_client.py`, `services/conversation_store.py`, `simple_db.py`, `schemas.py`):
- FastAPI app; agents are DB rows (system prompt + welcome greeting + voice + knowledge base) created/edited over a CRUD API, stored in a dedicated SQLite file (`data/legacy_app.db`, raw `sqlite3`, one shared connection + a lock).
- Outbound call: `POST /make-call` → Twilio REST → Twilio hits `/outgoing-call` for TwiML → `<Connect><ConversationRelay>` → our `/media-stream` WebSocket.
- **Twilio ConversationRelay does the STT and TTS.** Our server never touches audio, ever, on this path. The WebSocket exchanges plain JSON text (`{"type":"prompt","voicePrompt":"..."}` in, `{"type":"text","token":"..."}` out). Barge-in/VAD/interruption are Twilio's problem, configured via TwiML attributes (`interruptible="true"`), not ours.
- Per caller turn: Claude Haiku classifies sentiment (structured output) → conversation history + system prompt → Claude replies, **streamed** token-by-token back over the WebSocket.
- `POST /chat/test` exercises the same Claude logic over plain HTTP, no phone/Twilio needed — genuinely useful for iterating on a prompt.
- Transcripts + sentiment land in SQLite; readable via `GET /calls`, `GET /calls/{sid}`.

**Track B — the ShiftEaze scenario system** (`routers/scenarios.py`, `routers/voice_scenario.py`, `services/scenario_engine.py`, `services/scenario_store.py`, `scenarios/*.json`): this is the more sophisticated of the two live paths and appears to be the one actually in active use.
- Five HR calling scenarios (shift confirm, punch-in reminder, punch-out reminder, absence priority, OT request) × three languages (en/hi/gu), scripted as JSON knowledge bases — opening lines, branch replies, keyword hints — with **zero Python needed to edit a script**; `POST /scenarios/reload` hot-reloads the JSON.
- Also rides Twilio ConversationRelay, same as Track A, with per-scenario `transcriptionLanguage`/`ttsLanguage` TwiML attributes. Notably it works around a real Twilio/Google gap: Google Cloud STT has no `gu-IN` model, so Gujarati calls are transcribed with `hi-IN` and the classifier prompt is told to expect Devanagari-transliterated Gujarati — a genuinely clever, documented workaround, not an oversight.
- The AI's only job per turn is to classify the operator's utterance onto one pre-written branch (structured output, handles code-mixed Hindi/Gujarati/English, negation, volunteered-reason-before-being-asked); **the AI never writes the spoken words**, it only picks which scripted line to speak. That's a deliberate compliance property (HR-sensitive calls at scale) called out repeatedly in comments, and it's a good design.
- `POST /scenarios/preview`, `/scenarios/test-turn`, `/scenarios/test-batch` let you validate the full conversation logic with no phone, Twilio, or tunnel — and `preflight.py` / `START_HERE.md` are explicitly built around using these first.
- There's a real, live-call-tested rough edge already documented in code: a dead ngrok tunnel used to produce a silent "application error" call; `_check_tunnel_reachable()` now probes the tunnel before dialing and fails the API call instead. That's the kind of scar tissue you only get from an actual call having failed this way.
- Outcomes + facts land in the same SQLite file, a separate `scenario_calls` table; transcripts are shared with Track A's `messages` table.

**Both live tracks** also write a per-call JSON transcript file to `data/call_logs/<sid>.json` (`services/call_logger.py`) — a simple, working "replay a call's transcript" mechanism already, independent of the DB.

**`local_ai/`** — a genuinely separate, working, offline pipeline (faster-whisper STT → Ollama LLM → Piper TTS, file-in/file-out only, no mic/streaming mode). It's wired into Track B in exactly one place: `SCENARIO_LLM_BACKEND=local` swaps Claude for Ollama in the branch classifier. It has its own requirements file, its own README, its own tests, and — per that README — real measured numbers on the author's actual hardware (23–60s/turn on CPU, which is why it's explicitly gated as "offline/dev/QA only, not for live calls without a GPU"). This is the most relevant existing code for your stated long-term local-model goal, but it is not a real-time pipeline today — no VAD, no streaming, no barge-in; it's an offline batch tool.

**Test suite**: 39 test files' worth of unit/integration coverage for the *rebuild* pieces specifically — flow graph transitions, guardrail output-filtering, tool-registry idempotency (including a timeout test and an idempotency-key-is-order-independent test), the verbalize (number/time-to-speech) module, and a full `conversation_agent.run_turn` integration test with a fake LLM. All of it passed. This is unusually good test coverage for code that, per the next section, is not otherwise connected to anything.

## What calls out to Anthropic or other cloud APIs, and where

- **Anthropic/Claude** — `services/claude_client.py` is the only module that talks to Anthropic (lazy `anthropic.AsyncAnthropic` client, key from `ANTHROPIC_API_KEY`). Used for: streamed conversational replies (Track A, `generate_reply_stream`/`generate_reply`), sentiment classification (`classify_sentiment`, Haiku), scenario branch classification (`classify_structured`, used by `services/scenario_engine.py`, Track B), and two not-yet-called functions built for the rebuild (`generate_conversation_turn` — used by `services/agents/conversation_agent.py`, itself not wired to any router; `generate_supervisor_guidance` — no caller anywhere in the repo, likely a stub for a not-yet-written `supervisor_agent.py`).
- **Twilio** — `twilio.rest.Client` is called directly from `routers/calls.py` and `routers/scenarios.py` (both live paths) using `TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` straight from `config.py`. Separately, `services/telephony/twilio_provider.py` reimplements the same origination logic behind the `TelephonyProvider` ABC for the rebuild — **not called from any router**; the docstring in that file says outright it's "a lift of the logic that already lived in routers/calls.py."
- **Exotel / Plivo** — `services/telephony/exotel.py`, `services/telephony/plivo.py` implement the same ABC. Never imported outside `services/telephony/registry.py` and never reachable from an endpoint. Worth a close read before trusting them for a real call — I did not find evidence either has been exercised against a live account.
- **Deepgram** — `services/stt/deepgram.py`: constructor works, but `stream_transcribe` is `raise NotImplementedError(...)` with a comment explaining exactly why (needs a queue bridge around the SDK's callback interface, "left as the concrete Phase 2 task"). `deepgram-sdk` is deliberately **not** in `requirements.txt`.
- **Sarvam** (STT + TTS) — `services/stt/sarvam.py`, `services/tts/sarvam.py`: implemented against `httpx` directly (no SDK dependency issue), but I found no test coverage and no evidence of having been run against a real Sarvam key. Worth verifying against current Sarvam API docs before relying on it — the STT/TTS provider comments elsewhere in the repo are candid about being written to a documented shape, not smoke-tested.
- **ElevenLabs** — `services/tts/elevenlabs.py`: implemented (Flash model, chosen specifically for TTFB per a comment), `elevenlabs` package deliberately not in `requirements.txt`. Not tested against a real key as far as I can tell.
- **Azure Speech** — `services/tts/azure.py`: implemented, same caveate as above.
- **Odoo** — `services/integrations/odoo_client.py` sends HMAC-signed webhooks (`call.shift_confirmed`, `call.absence_intent`, etc.) to `ODOO_WEBHOOK_URL`. Only ever called from `services/tools/hr_tools.py`, which is only ever called from `services/agents/conversation_agent.py`, which — again — has no router. So today, nothing actually calls Odoo. The at-least-once delivery bookkeeping (`WebhookDelivery` rows, retry-sweep comment pointing at a `workers/postcall.py` that doesn't exist) is real design, just not running.
- **Ollama** (local, not cloud, but worth listing since it's an LLM call site) — `local_ai/llm_engine.py`, reachable only via `SCENARIO_LLM_BACKEND=local`.

## What's half-finished (built as interface/scaffolding, not reachable from any endpoint)

This is the bulk of what makes the repo feel bigger than it is, and it's almost entirely one coherent, well-thought-out unfinished effort rather than several unrelated ones:

- **`services/agents/conversation_agent.py`** — a full per-turn loop (flow graph → node-scoped prompt → tool calls with one resume round → slot-filling → output guardrail → next-node transition) that is genuinely well-built and has real test coverage, but is never imported by any router. There is no WebSocket or endpoint anywhere that drives a call through this loop.
- **`services/flow/*`, `services/agent_registry.py`, `configs/agents/*.yaml`, `configs/flows/*.yaml`, `prompts/agents/*/persona.j2`, `prompts/{base_persona,voice_output_rules,language_policy,guardrails,node_block}.j2`** — the config-driven multi-agent system the rebuild is aiming for (5 agents defined: `shift_confirm`, `punch_in_remind`, `punch_out_remind`, `absence_priority`, `ot_request` — the same five scenarios as Track B, reimplemented as a graph-based system instead of the branch-classifier system). `sync_configs_to_db()` runs on every server start (`main.py` → `simple_db.init_db()`... wait, actually **`db.init_db()`, not `simple_db.init_db()`** — see the Dead code / footguns section, this matters) and populates `Agent`/`AgentVersion`/`Prompt`/`FlowGraph` rows. So the config-sync machinery does run, but nothing ever reads those rows back to drive a live call.
- **`services/guardrails/*`** — real, tested, three-layer design (prompt instruction → fast regex classifier → a not-yet-written LLM-based post-call QA audit referenced in comments as `services/agents/qa_agent.py`, which doesn't exist). Only reachable through `conversation_agent.run_turn`, so also unreachable from a live call today.
- **`services/tools/*`** (`roster_tools.py`, `hr_tools.py`, `transfer_tools.py`, `comms_tools.py`) and the tool registry (`services/tools/registry.py`) — idempotent, timeout-guarded, auto-derives Claude tool schemas from Python type hints. Well-designed, well-tested, unreachable outside `conversation_agent.py`.
- **`models.py`'s compliance-relevant tables** — `Contact` (with `consent_status`, `consent_captured_at`, `dnc`), `ConsentRecord`, `Campaign`, `CallTask` (with `state`, `next_attempt_at`, `idempotency_key` — i.e. already shaped for a retry-aware dialer queue). **None of these tables are ever written to by any code path in this repo.** There is no endpoint to create a `Contact`, no code that checks `dnc`/`consent_status` before dialing (the `is_callable()` belt-and-suspenders check in `services/guardrails/input.py` reads `contact.dnc`/`contact.consent_status`, but nothing ever constructs a real `Contact` object to check), and no campaign/dispatch loop that would ever create a `CallTask`. `schemas.py` even has `CampaignCreateRequest`/`ContactCreateRequest` Pydantic models with no router using them. This is exactly the compliance-gate/dialer layer the master prompt asks for — the data model is a reasonable start, but there is currently **zero code enforcing DND/consent before a call goes out**, on either live track.
- **`services/dispatch/__init__.py`, `services/pipeline/__init__.py`, `workers/__init__.py`** — all three are empty files. Comments elsewhere reference modules inside them that don't exist yet: `services/dispatch/admission.py`, `services/dispatch/scheduler.py`, `services/pipeline/chunker.py`, `workers/roster_sync.py`, `workers/postcall.py`. This is the dialer/queue/concurrency-limiter/admission-control layer — currently 100% comment, 0% code.
- **`services/telephony/*`, `services/stt/*`, `services/tts/*` provider abstractions** — real ABCs, real provider-selection registries keyed off `settings.telephony_provider`/`stt_provider`/`tts_provider`, but nothing in either live call path uses them (both live paths hardcode Twilio + ConversationRelay directly). `services/telephony/base.py`'s own docstring says "Everything about the audio itself is Pipecat's job" — `pipecat-ai` is in `requirements.txt` labeled "Phase 2" but is not imported anywhere in the repo. This is the raw-media-stream, self-managed STT/LLM/TTS pipeline the master prompt assumes exists; it doesn't yet.
- **`services/verbalize.py`** — real, tested, and important: Hindi/Gujarati number/time-to-speech conversion so TTS doesn't read "14:00" as "fourteen hundred." Only used by... nothing yet (no import found outside its own test file), though it's clearly meant for the node-block prompt rendering path. Its own docstring flags the Gujarati number tables as "best-effort scaffold" needing native-speaker verification before a real pilot — a real, disclosed risk, not a hidden one.
- **`evals/__init__.py`** — empty. Comments in `services/guardrails/input.py` reference `evals/personas/prompt_injector.yaml`, which does not exist. The eval harness itself hasn't been started.
- **`services/telephony/twilio_provider.py`'s `transfer_call`** — comment: "requires a small TwiML endpoint... Wire url= below to that endpoint once it exists (Phase 5/7)." Acknowledged incomplete by the code itself.

## Security / secrets check (done as part of the audit, not a fix)

- `.env` is correctly listed in `.gitignore`. `.env.example` documents every variable with a one-line description already, in the shape the master prompt asks for.
- **`.env` on this machine is currently a byte-identical, unedited copy of `.env.example`** — confirmed via `diff`, no values read or exposed. That means: no `ANTHROPIC_API_KEY`, no Twilio credentials, no `NGROK_URL`, nothing. Right now, neither live call path can actually place or hold a call on this machine — `preflight.py` would fail loudly on `ANTHROPIC_API_KEY` if you ran it. This is the very first thing Phase 3 needs, ahead of any code change.
- No hardcoded secrets found in source. `services/integrations/odoo_client.py`'s HMAC signing and `preflight.py`'s masked key display (`...{key[-6:]}`) both show a working awareness of not leaking secrets into logs.
- One real prompt-injection-relevant gap worth flagging now rather than in Phase 2: `services/guardrails/input.py::scan_input()` detects injection patterns in what the operator says, but I could not find anywhere that `scan_input`'s result (`prompt_injection_flagged`) is actually checked or acted on — it's computed and, as far as I can tell, discarded. Also, Track A's generic agent (`routers/calls.py`, `routers/agents.py`) has **no injection scrubbing on user-supplied `system_prompt`/`knowledge_base` content at all** — a caller-facing agent whose knowledge base came from an untrusted CRM field would have no scrub in front of it today. Since the master prompt calls this out explicitly as a hard requirement, flagging it now: this needs to be designed, not just extended, since the one scrub function that exists isn't wired to anything.

## One correctness note worth a second look before Phase 3

`main.py` calls `simple_db.init_db()` (creates Track A's tables, seeds the `default` agent) — but `db.py`'s `init_db()` (the one that creates `models.py`'s SQLAlchemy tables *and* calls `agent_registry.sync_configs_to_db()`) is **never called from `main.py` at all**. I traced this specifically because it affects what "already runs today" means: the `Agent`/`AgentVersion`/`Prompt`/`FlowGraph`/`Contact`/`Campaign`/... tables in `models.py` are not actually created or populated when you run `uvicorn main:app`, contrary to what I assumed before checking. `db.init_db()` is only invoked from the test fixtures. Worth confirming with whoever's been running this locally whether that's intentional (rebuild genuinely not started) or a dropped wire-up.
